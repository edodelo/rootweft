# Rootweft v0.1.0-alpha Design

Date: 2026-09-20  
Status: approved for implementation  
Owner: edodelo

## 1. Purpose

Rootweft is an independent, local-first repository intelligence tool. It is an auditable structural knowledge-graph generator for Python, JavaScript, and TypeScript repositories, with lightweight Markdown indexing and optional ambiguity resolution through Jev. Coding agents and humans inspect its output through a CLI, a read-only MCP server, an Agent Skill, and a self-contained HTML viewer.

An optional decision layer uses TypeSafe AI's hosted Jev model to adjudicate bounded candidates. Jev does not discover arbitrary entities or generate explanations. Local parsers create candidates; Jev may validate a proposed relationship, select one canonical target from a finite set, or score relevance. The canonical local graph remains useful without a network connection or model key.

Rootweft is not a fork of Graphify and will not copy its code, tests, prompts, documentation, assets, or UI. Public documentation will describe it as an independent implementation and will not claim affiliation, endorsement, feature parity, or formal clean-room status.

## 2. Release Scope

The first release is `v0.1.0-alpha`. It includes:

- safe recursive scanning with configurable exclusions and resource limits;
- deterministic extraction for Python, JavaScript, and TypeScript;
- basic Markdown heading and symbol-mention extraction;
- stable node and edge identifiers with source evidence;
- full graph rebuilds into a versioned, canonical JSON format;
- local search, neighbor lookup, shortest paths, statistics, and explanations;
- optional Jev decisions through TypeSafe direct BYOK;
- an explicitly experimental OpenRouter provider;
- a read-only MCP stdio server;
- a portable Agent Skill and installer for major harness conventions;
- a self-contained, offline HTML viewer;
- public documentation, threat model, privacy and data-egress documentation;
- source distribution, wheel, checksums, SBOM, and a public GitHub release.

The release does not include natural-language question answering, free-form relationship generation, full document semantics, incremental watch mode, graph databases, PDF/image/audio extraction, multi-repository federation, IDE extensions, hosted services, or automatic repository modifications. Completion means satisfying this specification, not reaching general feature parity with Graphify.

## 3. Architecture

Rootweft uses four layers with one-way dependencies:

1. `scan`: validates the requested root, applies ignore rules and limits, and returns immutable file descriptors.
2. `extract` and `graph`: parse supported files, produce evidence-backed nodes and candidate edges, resolve deterministic relationships, and serialize the canonical structural graph.
3. `decide`: optionally sends bounded questions to a configured Jev provider and writes a separate adjudication overlay plus provenance. It depends on graph types, but graph construction never depends on a remote provider and remote decisions never delete or mutate the structural layer.
4. `interfaces`: CLI, MCP, skill installer, and viewer call public application services rather than parser internals.

Core packages must remain usable without MCP or remote-provider dependencies. Provider and MCP packages are adapters behind protocols so contract tests can use in-memory fakes.

## 4. Graph Model

The file format has schema identifier `rootweft.graph.v1`. Top-level `schema_version`, `extractor_version`, and `decision_policy_version` fields are mandatory. Output is UTF-8 JSON with keys sorted deterministically. Paths are POSIX-style and relative to the scan root. Consumers reject corrupt data or a newer unsupported schema explicitly rather than attempting a silent best-effort load.

The document has two named layers. `structural` is the immutable offline result. `adjudication` contains bounded candidates and remote decisions with `accepted`, `rejected`, `review`, or `error` state. Every query and response reports which layer was used.

### Nodes

Required fields:

- `id`: stable SHA-256-derived identifier;
- `kind`: `file`, `module`, `class`, `function`, `method`, `heading`, or `external`;
- `name` and optional qualified name;
- `language`;
- `evidence`: relative path and one-based start/end lines;
- `metadata`: bounded, JSON-compatible values.

### Edges

Required fields:

- `id`: stable identifier derived from source, target, relation, and callsite evidence, so separate callsites remain distinct;
- `source`, `target`, and `relation`;
- `origin`: `parser`, `resolver`, or `jev`;
- `status`: `accepted`, `proposed`, `rejected`, or `review`;
- `evidence` and optional decision provenance.

Initial relations are `contains`, `imports`, `calls`, `references`, and `mentions`. Parser-proven relations are accepted. Ambiguous calls, references, and mentions become bounded candidates.

### Jev provenance

A Jev decision records provider, immutable model identifier, question kind, question hash, option identifiers, returned probability distribution, model confidence when provided, decision policy, and timestamp. Choice options are local identifiers supplied by Rootweft; a model response cannot introduce nodes, relation types, paths, or commands. Raw API keys and full prompt state are never persisted. Evidence text is not stored twice.

## 5. Extraction and Resolution

Python uses the standard-library AST for `.py` and `.pyi`. JavaScript and TypeScript use pinned tree-sitter grammars for `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, and `.tsx`. Markdown uses a small deterministic parser for ATX headings, fenced-code exclusion, and exact symbol mentions.

Extraction never imports or executes repository code. Generated and vendor trees are excluded by default. UTF-8 with BOM is accepted; unknown encodings and binary files are skipped with diagnostics. Syntax errors preserve the file node and diagnostic but do not fabricate symbols. External imports become clearly marked external nodes. Dynamic imports, computed calls, and unresolved references remain unresolved rather than being guessed. Symbol tables are scoped by file and module. Deterministic resolution accepts exact imported or locally scoped matches. When multiple targets remain, the resolver emits a candidate set capped by configuration. Candidates carry the local evidence that produced them.

Stable identifiers are derived from normalized relative path, node kind, qualified name, and source location. Sorting occurs before serialization so the same tree and configuration produce byte-identical JSON.

## 6. Decision Layer

Jev is disabled unless the user provides both a provider and `--enable-remote`. The adapter is passed immutable candidate DTOs and has no filesystem, subprocess, graph-writer, or harness-configuration capability. Supported decision shapes are:

- Noul: whether one candidate relation is supported by supplied evidence;
- Choice: which target, including `none`, best resolves an ambiguous reference;
- Score: bounded relevance classification for a document-to-symbol mention.

The default policy is `review-only`: remote results are recorded as proposed/review decisions and do not alter parser-accepted edges. An explicit policy file may promote decisions, but every threshold and outcome remains in provenance. This avoids presenting uncalibrated probabilities as facts.

The direct provider defaults to immutable model `jev-1.13.0`. `jev-latest` is rejected for reproducible builds. OpenRouter lives behind provider name `openrouter-experimental`, uses a separate key, and is documented as an unstable intermediary. Provider selection is explicit and there is no automatic cross-provider fallback. Payload size, question count, option count, concurrency, and retry budgets are bounded. If a decision cache is enabled, its key includes payload, model, and policy hashes and its value omits source text.

Without `--require-remote`, a provider failure completes the structural graph and records overlay errors. With `--require-remote`, any incomplete required adjudication returns a non-zero exit code while leaving the structural artifact valid.

No generic `ask_jev` API or MCP tool is exposed. Rootweft is not a relay, model emulator, or data-collection service.

## 7. Privacy and Security

Network access is off by default. `--dry-run-egress` reports provider, candidate count, affected relative paths, and estimated bytes without making a request. Remote state contains only the minimum snippets required for the selected candidates.

Default exclusions cover `.git`, environment files, private keys, common credential files, virtual environments, dependency/vendor trees, caches, build output, and Rootweft output. A secret detector blocks suspicious snippets before egress and reports only category and relative location.

The scanner canonicalizes roots, rejects root escape, does not follow symlinks by default, rejects broken links and special devices, and enforces configurable limits for file count, individual bytes, total bytes, parse depth, nodes, edges, candidates, remote questions, retries, and estimated cost. Permission failures and files disappearing during a scan become explicit diagnostics.

Provider clients use fixed HTTPS origins, verified TLS, disabled redirects, bounded timeouts, and redacted exceptions. Retries apply only to transient timeouts, DNS failures, `429`, and selected `5xx` responses, honor `Retry-After`, and use bounded backoff. Authentication and other permanent `4xx` responses are not retried. Repository content is never logged. Rootweft has no telemetry. Offline and dry-run tests intercept socket creation to prove zero egress.

The HTML viewer performs no network requests. Graph data is embedded in a non-executable encoding, all labels are rendered as text, and a restrictive Content Security Policy blocks remote resources. Malicious HTML, SVG, URLs, ANSI/control characters, and oversized labels are covered by tests.

## 8. CLI and Error Handling

The executable is `rootweft`. Primary commands are:

- `rootweft build PATH --output GRAPH`;
- `rootweft search GRAPH QUERY`;
- `rootweft node GRAPH NODE_ID`;
- `rootweft neighbors GRAPH NODE_ID`;
- `rootweft path GRAPH SOURCE TARGET`;
- `rootweft explain GRAPH EDGE_ID`;
- `rootweft stats GRAPH`;
- `rootweft export-html GRAPH --output HTML`;
- `rootweft mcp GRAPH`;
- `rootweft provider-check --provider ...`.

Machine-readable commands support exact JSON output. Stdout contains only requested JSON/JSONL data or MCP protocol frames; diagnostics go to stderr. Configuration precedence is command flag, environment variable, project configuration, then built-in default. Exit codes distinguish usage/configuration, build/scan failure, incompatible schema, required-provider failure, and internal errors.

Individual unsupported or malformed files yield bounded diagnostics and do not abort a build. Root validation, output corruption, or exceeded global safety limits fail the command without replacing an existing good graph. Writes use a temporary sibling followed by atomic replacement; interruption, `Ctrl-C`, and failed exports remove incomplete temporary artifacts.

Provider failure never removes the local graph. Candidates become `review` with a redacted reason. Schema-invalid, non-finite, out-of-range, or mismatched Jev answers are rejected before graph integration.

## 9. MCP and Harness Compatibility

The MCP server uses the official Python SDK over stdio and exposes read-only tools:

- `graph_info`;
- `search_nodes`;
- `get_node`;
- `get_neighbors`;
- `shortest_path`;
- `explain_relation`.

It loads one explicit graph at startup and exposes no build, scan, export, filesystem-write, shell, provider, network, or generic model tool. Tool inputs never accept arbitrary filesystem paths. Results are paginated and capped. Every input has a bounded schema. A missing node is distinct from an empty result. Corrupt or incompatible graphs fail startup with a protocol-safe error. Server instructions treat repository text as untrusted data, never as agent instructions.

The distribution contains one canonical `skills/rootweft/SKILL.md`. An installer supports dry-run, project/user destinations, backups, and uninstall for:

- `.agents/skills/rootweft` for Codex, Gemini CLI, and compatible clients;
- `.claude/skills/rootweft` for Claude Code;
- `~/.hermes/skills/rootweft` or a selected Hermes skill directory;
- `.cursor/skills/rootweft` when requested.

The installer never edits `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, global MCP configuration, or shell profiles. Documentation provides copyable MCP snippets. The compatibility matrix records exact client version, OS, transport, test, result, and date. Claims use “tested with” for executed checks and “may work” for other MCP clients.

## 10. Viewer

The first viewer is intentionally small: graph statistics, text search, node detail, neighbor expansion, relation filters, layer selection, and evidence display. It is generated as one portable HTML file without CDN assets, external fonts, or network requests. Layout must remain usable for the included sample graph but is not intended to render arbitrarily large graphs at once; the UI caps visible nodes and returns an explanatory error rather than silently freezing. It warns that graph artifacts may contain proprietary source fragments.

## 11. Testing Strategy

Tests are written before production behavior. Required suites are:

- unit tests for scanning, permission failures, disappearing files, path handling, stable IDs, parsers, resolution, schema validation, queries, and atomic writes;
- golden tests proving byte-identical graph output across two builds;
- contract tests for direct and OpenRouter provider adapters using fake transports;
- malformed-response and retry tests;
- security fixtures for secrets, path traversal, symlink escape, special files, prompt injection, and viewer XSS;
- CLI tests for JSON output, stderr separation, and exit codes;
- MCP protocol smoke tests using the official client SDK;
- package installation tests from both wheel and source distribution;
- configuration and skill-installer tests on Windows and POSIX path conventions.

Normal CI performs no remote model calls. A protected manual workflow can run a live Jev smoke test with a user-provided secret. If that test cannot be run before the first release, release notes must label the adapter contract-tested but not live-verified; no production-readiness claim is allowed.

## 12. Packaging and Release

Rootweft targets Python 3.11–3.13 and uses a `src/` layout. Runtime dependencies are minimal and pinned by compatible ranges; development and release environments use lock files. Optional extras isolate MCP and remote-provider dependencies where practical.

The repository includes `LICENSE` (Apache-2.0), `NOTICE`, `ACKNOWLEDGMENTS`, `THIRD_PARTY_NOTICES.md`, `PROVENANCE.md`, `SECURITY.md`, `PRIVACY.md`, `DATA_EGRESS.md`, `THREAT_MODEL.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, and `CHANGELOG.md`. Branding states that Rootweft is independent and not affiliated with or endorsed by Graphify Labs, TypeSafe AI, or OpenRouter.

Because Jev is a proprietary hosted service and the referenced TypeSafe acceptable-use-policy URL was unavailable during design research, the alpha labels the adapter experimental, requires users to accept the provider's current terms directly, and makes no production-readiness or retention guarantee.

CI runs lint, type checking, tests, coverage, build/install checks, dependency audit, secret scanning, and a cross-platform Python matrix. GitHub Actions are pinned to commit SHAs with least-privilege permissions. Release artifacts include wheel, source distribution, SHA-256 checksums, and an SBOM. The public release tag is `v0.1.0-alpha`.

## 13. Acceptance Criteria

The release is acceptable when:

1. A fixture containing Python, Python stubs, JavaScript, JSX, TypeScript, TSX, and Markdown builds successfully offline with expected nodes, imports, calls, and evidence.
2. Two identical builds produce byte-identical graph JSON on each supported OS, and pinned environments produce the same graph hash across Windows, Linux, and macOS.
3. Adding unrelated source lines does not change existing unaffected identifiers, and separate callsites keep separate edge IDs.
4. Dynamic calls remain unresolved rather than becoming certain edges.
5. Search, neighbors, path, explanation, statistics, and HTML export work on the fixture.
6. No socket can be opened in offline or dry-run modes; no network call occurs without `--enable-remote`.
7. Secret-bearing evidence, symlink escape, traversal, environment files, credential files, and vendor trees are blocked before a fake provider receives data.
8. Fake Jev Noul, Choice, and Score responses cover accepted, rejected, review, timeout, and invalid-schema outcomes with complete provenance.
9. Optional remote failure leaves the structural layer valid; required remote failure returns the documented non-zero code.
10. MCP SDK smoke tests pass with clean stdout, bounded results, and no mutating or provider tools.
11. The viewer passes malicious-content tests and makes no network request.
12. CLI machine output is always valid JSON/JSONL and uses documented exit codes.
13. Wheel and source distribution install in clean environments and expose `rootweft`.
14. CI covers the supported Python versions on Linux, macOS, and Windows.
15. The compatibility matrix contains only verified Codex, Claude Code, and Hermes claims with versions and dates.
16. Release assets include checksums, SBOM, licensing, notices, privacy/security policy, and provenance.
17. No copied Graphify material, secret, High/Critical dependency vulnerability, or unresolved release-blocking security finding remains.
18. The public GitHub repository and release artifacts match the verified local tag.

## 14. Architecture Decisions

- ADR-001: immutable structural graph plus a separate Jev adjudication overlay.
- ADR-002: MCP is confined to reading one precompiled graph.
- ADR-003: providers are explicit and never fall back across data destinations.
- ADR-004: schema, identity, and serialization are versioned and portable.
- ADR-005: the viewer is standalone and treats all repository-derived strings as hostile.

## 15. Success Measures

For the alpha, success means a new user can install Rootweft, build and inspect the sample repository entirely offline, connect a tested MCP client, and optionally produce auditable Jev proposals using their own key. Performance and graph-quality benchmarks are recorded as baselines rather than marketed as parity claims.
